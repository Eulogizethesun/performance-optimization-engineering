# 分阶段统计与 perf 分析

两件事分工：

- **分阶段统计**：时间花在哪一段。
- **perf 分析**：这一段里 CPU 在做什么；如果不在算，再看它在等什么。

---

## 一、分阶段统计

### 1. 定义阶段

- **先切第一层**：按路径的自然边界分段，不预设段数。
- 段与段**互斥且覆盖**：同一时刻只属于一段；所有段之和 + 残差 = 总时长。
- **优先拆平均耗时最高的几段（通常 1–3 段），不必只拆一段**；重复到定位到瓶颈（能说清工作项、次数、单次成本），或确认受限于某个物理上限。
- 父段包含子段时，只对**叶子段**求和，否则重复计数。
- 异步/后台工作单独成段，不要混进主路径。

### 2. 采集

| 方式 | 要点 |
|---|---|
| 边界打点 | 单调时钟；记录 start/end、request id、stage id、线程/进程 |
| 日志 | 先确认日志时间是"工作起点"还是"异步输出时间" |
| trace/span | parent/child 关系明确；父子不要同时计入总时长 |
| 采样 | 高 QPS 可采样，但必须记录采样率；低 QPS 尽量全量 |
| 失败/重试 | 重试是额外段，不要覆盖原段；失败请求单独统计 |

### 3. 聚合

发现阶段的**主指标是平均每次操作的耗时**（以及由它算出的总时长与占比）。分位数只在问题本身是尾延迟时才用。

每个阶段至少给：

```text
次数/请求、每次请求耗时、单次调用平均、占比
```

`单次调用平均 = 每次请求耗时 ÷ 次数/请求`；`总成本/秒 = 每次请求耗时 × 请求频次`。

再按需要归一化：

- 每请求（平均每请求花在该段多少 ms）
- 每秒/每天（总成本）
- 每操作类型/每版本/每配置（同一统计方式对比）

检查**覆盖率**：`已归属时长 / 总时长`。残差大，先补打点，不要猜。

### 4. 呈现

| 阶段 | 次数/请求 | 每次请求耗时 | 单次调用平均 | 占比 | 备注 |
|---|---:|---:|---:|---:|---|
| 网关 | 1 | 12 ms | 12 ms | 7% | |
| 数据访问 | 51 | 100 ms | 2 ms | 60% | 逐条查询 |
| 序列化 | 1 | 18 ms | 18 ms | 10% | |
| 其他/残差 | — | 37 ms | — | 23% | |

结论写成"最大段 + 该段内部的工作项（次数 × 单次成本）"，不要停在"数据访问占 60%"。

### 5. 物理上限分析

即使硬件不能换，也要在结论里给出：

- **受限资源**：网络 RTT/带宽、磁盘 IOPS/吞吐、内存带宽、CPU 频率/核数、缓存大小、缺页。
- **理论下界**：字节 ÷ 带宽、次数 × 单次成本、RTT × 往返数、指令数 ÷ IPC ÷ 频率。
- **利用率**：实际 / 理论；>70–80% 接近上限，<30% 说明软件还有空间。
- **结论**：当前受限于 X，利用率 Y%，软件优化最多到 Z；再低需要改数据量/布局/并行/硬件。

### 6. 常见错误

- 把日志输出时间当工作起点（异步批量输出）。
- 跨进程混用时钟（只比 duration，不比绝对时间戳）。
- 并列阶段相加，超过总时长。
- 漏掉排队、锁、重试、GC。
- 阶段定义随版本变化，却直接比数值。
- 只统计成功请求。
- 问题本身是尾延迟，却只看平均。
- 采样率变化没记录。

## 二、perf 分析

### 1. 先选工具

| 问题 | 工具 |
|---|---|
| CPU 周期/指令/缓存/分支 | `perf stat` |
| 哪个函数热、调用链 | `perf record -g` + `perf report` / 火焰图 |
| 系统调用次数与耗时 | `perf trace` / `strace -c` |
| 锁争用 | `perf lock` |
| 调度与 off-CPU 等待 | `perf sched` / off-CPU 分析 |
| 缺页/内存 | `perf stat -e page-faults` / `/proc` |
| 非 Linux | ETW/WPA、Instruments、JFR、pprof；结构相同 |

### 2. perf stat：先看整体

```bash
perf stat -e cycles,instructions,cache-misses,branch-misses,context-switches,page-faults -- ./app
```

读法：

- **IPC 低** → 内存停顿、分支错误、依赖链长。
- **cache-misses 高** → 局部性差、工作集太大。
- **context-switches 高** → 锁、调度、阻塞。
- **page-faults 高** → 缺页、内存压力、冷启动。

对比两个版本/配置时，workload 必须相同；否则数字不可比。

### 3. perf record / report：找热函数

```bash
perf record -F 99 -g -- ./app
perf report --stdio --no-children   # self time
perf report --stdio --children      # inclusive time
```

- **self time**：函数自身耗时。先看 self，找真正消耗 CPU 的叶子。
- **children/inclusive**：含被调用者。用来看路径，不要用它判断"谁最贵"。
- 火焰图：宽度 = 采样占比，栈深 = 调用链；找**宽平台**；叶子宽 = 自身耗时；不要只看塔尖。
  生成：`perf script | stackcollapse-perf.pl | flamegraph.pl > out.svg`。
- 符号：编译带 debug info；strip/静态二进制可能无符号；JIT 需要 perf map。
- 采样频率：99 Hz 足够看热点；过高会增加开销与偏差。
- 内核/用户分开看；权限受限时用 `--call-graph dwarf` 或 frame pointer。

### 4. 从 profile 到工作项

对 self time Top 10 逐个问：

1. 它在做什么工作？
2. 每次操作调用多少次？
3. 单次成本多少？
4. 这个工作量能不能减少（少做、合并、缓存、换算法）？

组合判断：

- **宽而浅**的调用路径 → 大量重复/放大。
- **窄而深** → 单次复杂或依赖链长。
- profile 给占比，计数器给次数，两者相乘 = 绝对成本。

不要直接优化最热函数；先看它处理的量是否本可减少。

### 5. 常见错误

- profile 的是合成负载/错误配置/错误版本。
- 没有符号或内联，归因到错误的函数。
- 只看 self 不看 children，或反之。
- 采样频率过低（漏热点）或过高（开销/偏差）。
- 把 profiler 开销算进被测路径。
- on-CPU profile 看不到 IO/锁等待，误判"CPU 不是瓶颈就没有瓶颈"。
- 把"热"当"可优化"。

## 三、串起来

```text
分阶段统计 → 最大段
  ├─ 该段在算 → perf record/stat 看热函数与硬件指标
  ├─ 该段在等 → 计数/trace/锁/IO 指标看等待对象
  └─ 该段在搬运/放大 → 工作账本看次数 × 单次成本
差分 → 确认改动真的减少了工作量
```

分阶段统计回答"哪里"，perf 回答"在做什么"，计数器回答"多少次"，差分回答"改了有没有用"。

# 四条发现路径

四条路径互相补盲：A 找大项，B 找具体工作，C 验证异常，D 判断还有多少空间。例子中的数字均为示意。

---

## A0 先用现成数据排 Top-N

A 的第 0 步。先看系统已经记录了什么，按**总成本**（次数 × 单次成本）排序，不是按单次耗时。

| 数据源 | 排序键 | 能发现 |
|---|---|---|
| 接口监控 | 平均耗时 × QPS，或总耗时占比 | 最值得优化的接口 |
| 数据库统计/慢查询 | 调用次数 × 平均耗时 | N+1、全表扫描、缺索引 |
| 下游调用统计 | 次数 × 平均耗时 × 放大倍数 | 逐条 RPC、重试放大 |
| profiler | self time / total time | 热函数、重复计算 |
| 系统调用/IO 统计 | 次数 × 单次成本 | 小 IO、系统调用风暴、重复 fsync |
| 分配/GC 统计 | 分配速率、停顿、存活对象 | 高频分配、缓存泄漏 |
| 锁/队列指标 | 等待时间、队列长度、拒绝数 | 争用、池过小、无界队列 |
| CI 分阶段 | 各阶段 wall × 频次 | 重复下载、全量编译、串行测试 |
| 启动打点 | 各阶段耗时 | 串行初始化、多余加载 |

规则：先看 Top 10；50 ms × 1 次/秒 不如 5 ms × 1 万次/秒；没有监控就用日志/代码估次数。

---

## A 自上而下

1. 选一个用户可感操作，写清起点/终点。
2. 先切第一层路径（按自然边界，不预设段数），标同步/异步、跨进程/跨网络、读写。
3. 每段填时间（实测或估）与工作量（次数 × 单次成本）。
4. **优先拆平均耗时最高的几段（通常 1–3 段），不必只拆一段**；重复，直到定位到瓶颈（能说清工作项、次数、单次成本），或确认受限于某个物理上限。
5. 对每个叶子段问五问。

```text
请求 200 ms
├─ 网关/鉴权 15
├─ 业务 CPU 30
├─ 数据访问 120   ← 最大段
│  ├─ 主查询 1 × 20
│  └─ 详情查询 50 × 2 = 100   ← 放大
├─ 序列化 20
└─ 网络/排队 15
```

结论不是"数据库慢"，而是"50 次详情查询本可合并"。

陷阱：最大段可能是物理上限（RTT/带宽/IOPS），继续拆代码无用；时间分布平均时改看工作量；只拆到函数不算拆完；段间排队、锁、重试也要算。

---

## B 自下而上

1. 从 trace、日志或入口确定**真正高频执行**的路径，不要从最底层开始。
2. 每遇到循环、IO、加锁、分配，问：做什么工作？多少次？结果给谁用？能不能不做/少做/晚点/换地方？
3. 用 `02-waste-taxonomy.md` 的 12 类对照。
4. 记成"工作项 + 次数 + 成本"，不要当场改代码。

```text
for (item : items) {
  detail = db.query(item.id);          // 50 次查询
  log.info("item={}", toJson(item));   // 热路径同步日志 + 序列化
}
response = json.write(items);          // 再序列化一次
```

三个候选：批量查询、日志异步/降级、避免重复序列化。

陷阱：读冷代码（一年跑一次）；只读业务代码，漏掉框架/中间件/序列化/日志；把"代码丑"当"性能差"；忽略配置与构建。

---

## C 差分

1. 找两组可比样本：旧/新版本、A/B 配置、快/慢机器、正常/异常副本、自己/同行。
2. 只改一个变量。
3. 记录差异出现在哪一段、哪类工作、哪个资源。
4. 解释差异；解释不了就是候选。

```text
A 机房平均 80 ms，B 机房 200 ms
版本/配置/数据量/CPU 相同
→ B 跨可用区访问数据库：1 ms × 50 次 = 50 ms
→ 其余 70 ms 来自排队与缓存差异（示意）
```

陷阱：同时改多个变量；环境漂移；比较不同工作负载；问题在尾部时只看平均（差异可能被平均掩盖）。

---

## D 理论

1. 数工作量：字节、行、页、调用次数、锁次数。
2. 用数量级成本算理论时间（见 `01-work-model.md`）。
3. 比较：
   - 实际 ≈ 理论：已在物理限制附近，改数据量/布局/并行，不是改代码。
   - 实际 ≫ 理论（10 倍以上）：有等待、放大、争用或额外搬运。
   - 实际 ≪ 理论：成本模型或工作量统计错了。
4. 把缺口拆成"必要工作 + 额外工作"，后者是候选。

**物理上限不是终点**：即使硬件不能换，也要写清受限资源、理论下界、实际/理论利用率、剩余空间。例：网络 RTT × 往返数、字节 ÷ 带宽、次数 × IOPS 成本。利用率 >70–80% 接近上限；<30% 说明软件还有空间。结论要能回答"改软件最多到多少，再往下需要改数据量/布局/并行/硬件"。

```text
读 1 GB，设备 2 GB/s → 理论 0.5 s；实际 3 s → 6 倍缺口
→ 查随机读、读放大、重复读、串行请求，而不是换更快的盘
```

陷阱：单次成本错一个量级；忽略并行与排队；忽略尾延迟；把物理限制当代码问题。

## 三角验证

| 组合 | 用途 |
|---|---|
| A + B | 大段 → 具体浪费，最常用 |
| A + D | 大段接近理论下界 → 改数据量/架构，别再拆代码 |
| B + C | 可疑写法 → 差分确认它真的影响结果 |
| C + D | 异常 → 用理论判断还有多少空间 |

两条以上同向 → 候选；只有一条 → 待确认；首轮全部列出。

## 陌生工程第一周

| 时间 | 动作 | 产出 |
|---|---|---|
| 第 1 天 | 盘点入口，按耗时 × 频次排 Top 20，选 3 个目标 | Top-N + 3 个目标 |
| 第 2 天 | 画 3 张路径图：同步/异步、跨进程/跨网络、读写、锁 | 路径图 |
| 第 3–4 天 | 沿热路径读代码与配置，12 类对照，填工作账本 | 3 份账本 + 浪费清单 |
| 第 5 天 | 汇总 20 个候选，算上界/置信度，排序，选 3 个确认 | 候选清单 + 确认计划 |

第一周不改代码；目标是把"哪里可能浪费"从感觉变成有次数、有成本的清单。

# 判断与结论自检

用法：在选候选、确认证据、下结论/上线前，按对应表逐行校验。"怎么验证"一列都是可以立刻执行的动作。

---

## 一、选候选时

| 容易犯的判断 | 问题在哪 | 怎么验证 |
|---|---|---|
| 热点就是瓶颈 | 热点可能只是在处理上游放大的量 | 查它的调用次数与处理量，确认工作量能否减少 |
| CPU 高就是代码慢 | 可能是自旋、忙等、重复计算 | 看 IPC、指令数与调用次数，区分计算密集和空转 |
| 并发一高就是锁 | 也可能带宽、池、队列、头阻塞 | 比较每单位成本，测锁等待占墙钟的比例 |
| 单次慢一定是算法问题 | 也可能 RTT、冷缓存、首次初始化 | 分别测冷/热与相同数据规模 |
| 代码看起来低效就一定慢 | 频次可能极低 | 算频次 × 单次成本 |
| 慢只可能出在自己写的代码里 | 框架、中间件、序列化、日志也在热路径 | 沿完整路径看，不只业务代码 |
| 内存没满就没有内存问题 | 分配压力、GC、拷贝、缓存污染、缺页都可能与容量无关 | 看分配速率、GC、缺页与缓存命中 |
| 磁盘不忙就没有 IO 等待 | 写可能在页缓存；读可能被预读掩盖；等待可能在元数据或队列 | 看 IO 延迟、队列深度与页缓存命中 |
| 工具没覆盖到就没有问题 | 锁等待、IO 排队、跨进程常在盲区 | 补计数、trace 或阶段统计 |
| 到了物理上限就没有优化空间 | 硬件不能换，但仍需量化受限资源与余量；软件可能还有空间 | 算理论下界与利用率，写清受限资源 |

## 二、确认证据时

| 容易犯的判断 | 问题在哪 | 怎么验证 |
|---|---|---|
| 计数器动了就是收益 | 只证明机制发生 | 测端到端或用户指标 |
| 组件快 2 倍，整体就会快 2 倍 | 组件占端到端比例可能很小 | 算组件占端到端比例 |
| 缓存热了就是算法好 | 数据可能只是在内存里 | 冷/热分别测 |
| 合成负载能代表真实负载 | 数据分布、并发形态、失败率不同 | 用真实样本或回放 |
| 单次观测就是规律 | 波动、漂移 | 换窗口或机器复现 |
| 平均值正常就没问题 | 若问题本身是尾延迟，尾部可能已坏 | 尾延迟问题单独看尾部，否则看平均与总量 |
| 重试后成功就是成功 | "慢成功"污染分布，也掩盖故障 | 单独统计失败与重试 |
| 相关就是因果 | 可能被第三个因素驱动 | 做差分或找机制 |
| 没看到失败就说明路径没问题 | 失败与重试路径可能更贵 | 单独统计失败与重试路径 |
| 日志里的总量就是实际工作量 | 总量可能是被扫描或遍历的总量，不是实际处理的量 | 先定义分子/分母，再核对页/字节/行数 |

## 三、下结论/上线前

| 容易犯的判断 | 问题在哪 | 怎么验证 |
|---|---|---|
| 优化 A 不会伤 B | 吞吐、延迟、内存、成本会交换 | 看护栏指标 |
| 已到物理上限，所以没空间了 | 必须给出受限资源、利用率与剩余空间，否则结论没有参考价值 | 算理论下界与实际/理论比 |
| 数据量/分布变了，却当成代码退化 | 同一份代码会因数据变化而变慢 | 对齐数据再比 |
| 环境差异当成版本差异 | 机器、缓存、邻居干扰 | 同窗口交替 |
| 局部指标就是用户感知 | 端到端还含网络、重试、排队、渲染 | 测端到端指标 |
| 一次演示或单次运行就是结论 | 环境、数据、并发可能不真实 | 在接近生产的场景复现 |
| 没有性能回归就等于没有风险 | 性能与正确性、失败路径是两回事 | 跑正确性、失败注入与长跑 |

---

**一句话**：先说清"哪些工作本来不必做、受限于什么资源"，再说"它有多快"。
